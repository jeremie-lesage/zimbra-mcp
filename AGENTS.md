# Contributing to zimbra-mcp

Guidelines for anyone changing this repository, human or AI coding agent. Read them before
opening a pull request.

## Project layout

- `src/zimbra_mcp/server.py`: FastMCP entry point. The lifespan registers the tools, then tries
  to log in (a 2FA account starts without a session).
- `src/zimbra_mcp/config.py`: `ZimbraConfig`, loaded from environment variables.
- `src/zimbra_mcp/client.py`: `ZimbraClient`, synchronous SOAP calls through `python-zimbra`,
  plus the REST attachment download.
- `src/zimbra_mcp/errors.py`: exceptions, all derived from `ZimbraMCPError`.
- `src/zimbra_mcp/tools/*.py`: one `register_*_tools(mcp, client, ...)` function per domain.
  Tools are closures declared with `@mcp.tool()` that capture `client` (and `config` when needed).

## Zimbra SOAP

- Mail operations use the `urn:zimbraMail` namespace; authentication uses `urn:zimbraAccount`.
- Zimbra returns a single dict or a list depending on the number of results: always normalize
  with `if not isinstance(x, list): x = [x]`.
- Dates are milliseconds since the epoch.
- Message actions go through `MsgActionRequest` (`move`, `read`, `trash`, `delete`, `tag`).

## Safety rules

The model driving these tools reads email content written by third parties, so treat every tool
as reachable by a prompt injection:

- Anything irreversible or outward-facing is opt-in through an environment variable
  (`ZIMBRA_ENABLE_SEND`, `ZIMBRA_ENABLE_HARD_DELETE`). A tool that is off is either not registered
  or returns `{"success": False, "error": ...}`. Defaults stay safe.
- Deletion goes to the Trash unless hard delete is enabled and explicitly requested.
- Filenames, paths and HTML coming from an email or from the model are untrusted: sanitize them
  (`_safe_filename`, `_sanitize_html`) and never write outside the target directory.
- Never put the auth token or the password in a URL, a log line, an error message or `repr()`.
- Keep logging at `INFO`: in `DEBUG`, the MCP SDK logs every message, email bodies included.
- Do not hard-code values that depend on the server configuration (session lifetime, limits):
  read them from the response or make them configurable.

## Code style

- Python 3.10+, type unions with `|`.
- Guard clauses: handle the edge case first and return, then write the main case without nesting.
- No explanatory comments. If something deserves an explanation, it belongs in the README or in
  the commit message. Docstrings document public tools and functions, not the implementation.
- ASCII punctuation in code, docs and commit messages (a plain hyphen, no em or en dash).
- Prefer editing an existing module over adding a new one; reuse the existing helpers.
- New dependencies go in `pyproject.toml` with `uv.lock` regenerated by `uv lock`.

## Tests

```bash
uv sync --extra test
uv run pytest
```

- No network: mock `ZimbraClient._comm` and `_token`, or the client method a tool calls.
- `tests/conftest.py` provides `config`, `connected_client` and `capture_tools()`, which returns
  the registered tool functions by name.
- Every behaviour change comes with a test; module-level helpers are tested directly.
- All tests must pass before you open a pull request.

## Commits and pull requests

- Branch from `develop` and target `develop`. Rebase on the latest `develop` before opening the
  pull request so it merges without conflicts.
- Conventional Commits in English: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, with an
  optional scope (`feat(emails): ...`). Keep the subject line short enough not to be truncated.
- No `Co-Authored-By` trailer, including the one added by AI assistants.
- One topic per pull request. Check open pull requests first to avoid overlapping work.
- Do not commit diagnostic scripts, editor settings or personal tool configuration
  (`.vscode/`, `.idea/`, `.claude/`, `.mcp.json`).
- Update the README when you add a tool, a parameter or an environment variable, and add the
  variable to `.env.example`.
